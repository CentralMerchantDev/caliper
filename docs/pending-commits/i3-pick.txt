I3: pick -- what was clicked stays selected

What was wrong: public/world-render-3d.js's city-mode click handler already
raycast a click to a world point and asked the spatial index what was there
("CITY MODE PICKS AGAINST THE SCENE" -- that mechanism predates this step
and was never broken). It called `this._index.addressAt(x, z)` fresh on
every click and kept nothing: D1's createSelection() (public/selection.js)
was proven correct in isolation and never wired in, so a later "describe
this" request (D2/D4) would have had nothing to read.

How it's fixed: constructs `this._selection = createSelection(this._index)`
alongside the spatial index, and the city-mode handler now resolves through
`this._selection.pick(x, z)` instead of the index directly -- same address,
now persisted at `.current`. "Something on screen naming what is picked"
was already true (the existing onInspect callback populates the HUD) and is
unchanged.

Two tests, at the two levels this codebase actually verifies renderer code:
  - test/pickSelection.test.ts's DATA test, against the real generated plan
    (not a fixture): a pick at a real plot's real centre returns that exact
    plot's id and it stays at .current; a second pick on a different plot
    replaces the first (one selection, not a history).
  - The same file's WIRING test, reading world-render-3d.js's own source
    (constructing a real WorldRenderer needs a GPU this suite does not have
    -- the same limitation test/rendererStatic.test.ts already states and
    works around the same way): pins that the city-mode handler resolves
    through this._selection.pick, not this._index.addressAt directly.

Mutation city-mode-pick-resolves-through-persisted-selection (reverts the
handler to call the index directly) CAUGHT:
