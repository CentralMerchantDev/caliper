TWO DIFFERENT CHECKS, DELIBERATELY SEPARATE (test/deployManifest.test.ts):

1. The page's own spans vs test/deployManifest.generated.json --
   the same shape every other generated claim in this project already
   gets. Three new pure comparators in src/generatedClaimChecks.ts
   (deployVersionClaimMismatch/deployCommitClaimMismatch/
   deployBuildTimeClaimMismatch), same file every other claim's own
   comparator already lives in -- one source of truth for "is this
   published number stale."

2. "MATCHES WHAT BUILT IT" -- SHIP-5's own harder clause, and not
   provable by comparing two generated artefacts (both could drift
   together, or the JSON could simply be hand-edited to agree with a
   stale page -- the exact "declared value in a second place, nothing
   binding them" shape AUDIT-PROTOCOL.md's own Failure pattern B names).
   Checked against the REAL, LIVE git history instead: `git cat-file -e
   <commit>` (the declared commit is a real object in this repo, not a
   hand-typed string that merely looks like one) and `git merge-base
   --is-ancestor <commit> HEAD` (it is HEAD or a genuine ancestor of it,
   not a commit from a different branch or a dangling object).

NOT STRING EQUALITY AGAINST CURRENT HEAD, AND THAT IS DELIBERATE: the
generator's own embedded commit is read at generation time, before the
commit that carries this very change exists -- it is necessarily the
PARENT commit, not a prediction of its own future hash (which cannot be
known in advance; a file cannot embed the hash of the commit that adds
it). A test asserting equality to CURRENT HEAD would go red the instant
this commit itself lands. The ancestor check is what turns "the commit
this page was built from" into a real, standing claim instead of one
that only holds for a single moment.
