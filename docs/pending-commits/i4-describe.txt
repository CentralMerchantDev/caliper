What was wrong: D2's makeDescribeRequest (public/describe-request.js) was
proven correct in isolation (test/describeRequest.test.ts) and never wired
into the running page -- nothing imported it. The existing text box in the
app (#bar-request-input/#bar-submit) drives the pre-existing "startRun"
pipeline against parcel ids, a different, older addressing scheme; I5 is
where that path and the new one meet, not this step.

How it's fixed: public/index.html gained #describe-input/#describe-submit/
#describe-result inside the existing parcel-inspect panel (the one I3's
onInspect already shows on a real pick) -- a free-text box, no option list.
Its click handler calls makeDescribeRequest(renderer3d.getSelection(), text).
getSelection() is a new, small delegate method on the WorldRenderer wrapper
(public/world-render-3d.js), returning the real, persisted _selection I3
wired in, or null in the 2D fallback. The result -- the resolved address and
the typed text -- is displayed with .textContent only, on the one path any
visitor-typed text reaches the DOM.

Two tests, reading index.html's own source (it is markup with an inline
module script, not importable as an ES module in Node -- the same
constraint test/rendererStatic.test.ts and test/pickSelection.test.ts
already state and work around the same way):
  - the handler reads the real selection (renderer3d.getSelection()) and
    calls makeDescribeRequest -- not a stale or fabricated value.
  - the result is written with .textContent, never .innerHTML.
