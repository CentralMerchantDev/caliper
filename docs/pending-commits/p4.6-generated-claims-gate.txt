P4.6 -- one command for every generated claim, and one gate that names
every stale one at once instead of three tests that each catch a third

WRONG: three separate generated claims (the test counts, the city summary,
and through it the building count) are regenerated by two different
scripts, run at different times, by whoever happened to be touching
whichever one -- and each has drifted independently this week, every single
time found by accident while chasing something else. This session's own
knot-fix pass found the building-count drift (17,105 -> 17,108) while
fixing the unrelated test-count knot; that is the third such accidental
find, not the first.

WHAT WAS BUILT:

- scripts/gen-claims.mjs -- one command that calls scripts/gen-city-
  summary.mjs then scripts/gen-test-count.mjs (does not duplicate or
  replace either), and reports which generated files actually changed.
  `npm run gen:claims`. Accepts --node-log/--worker-log, passed straight
  through to gen-test-count.mjs's own flags, so regenerating everything
  does not force a second full-suite run when a caller already has one
  captured.

- src/generatedClaimChecks.ts -- the pure comparison behind every
  generated claim, one function each (settlementsClaimMismatch,
  buildingsClaimMismatch, nodeTestsClaimMismatch, workerTestsClaimMismatch,
  claudeMdClaimMismatch), extracted so EVERY comparison is independently,
  synthetically testable with a deliberately wrong value -- the same shape
  settlementsClaimMismatch already had, generalised to the other four
  claims instead of inlining each one's equality check separately.
  publicClaims.test.ts and test/claudeMdIsCurrent.test.ts now call these
  same functions instead of repeating the comparison logic inline -- one
  comparison per claim, checked from as many places as care to, not one
  comparison per file that happens to check it.

- test/generatedClaimsAreCurrent.test.ts -- P4.6's own consolidated gate.
  checkAllGeneratedClaims() walks a manifest of all five claims above
  against the real, current files and returns every stale one; the gate
  test asserts the list is empty and, if not, names EVERY stale claim in
  ONE failure message, not just the first. "No published number is stale"
  is now one property with one assertion, not three tests a reader has to
  run and correlate themselves.

A REAL DEFECT FOUND WHILE BUILDING THIS, CAUGHT BEFORE IT SHIPPED: the
first version imported settlementsClaimMismatch directly from
publicClaims.test.ts. test/run.mjs bundles and imports every .test.ts file
independently, and a relative test-to-test import gets the WHOLE imported
file's code -- registrations included -- inlined into the importer's own
bundle. Measured directly: running both files together made "the test
counts on the page are the test counts" execute twice. Fixed by moving the
shared comparisons out of test/ entirely, into src/generatedClaimChecks.ts,
which is not independently discovered or bundled-with-side-effects by
test/run.mjs. Confirmed fixed: the same two-file run now shows the test
exactly once.

HOW IT IS KNOWN TO BE FIXED, WATCHED RED FIRST PER MARK'S OWN INSTRUCTION:

- Each of the five pure comparison functions has its own synthetic test
  calling it directly with a deliberately wrong value (a staled building
  count, node-test count, worker-test count, CLAUDE.md line, and an
  unreadable CLAUDE.md line) and asserting the exact message returned --
  the same style settlementsClaimMismatch's own pre-existing test already
  used, applied to the other four.
- checkAllGeneratedClaims()'s own aggregation is separately tested: with
  one entry's input deliberately wrong, the gate reports EXACTLY that one
  claim as stale, not all five and not silently none -- the property this
  whole pass exists for, checked directly rather than assumed from the
  individual pure-function tests alone.
- One further mutation watched red for real and reverted: disabling
  buildingsClaimMismatch's own comparison (`if (false && ...)`) correctly
  turned its synthetic test red while the real-data gate test stayed green
  (the real page and real generated file currently agree either way) --
  named explicitly, and the synthetic test is what is recorded in
  test/mutations.json for this control, since it is the one this specific
  mutation is actually checkable against.
- The double-bundling defect above was itself caught by direct measurement
  (grepping the real suite's output for a duplicate test name), not
  assumed absent -- recorded in src/generatedClaimChecks.ts's own header so
  the next shared-test-helper does not repeat it.
- Regression: test/publicClaims.test.ts, test/claudeMdIsCurrent.test.ts,
  test/generatedClaimsAreCurrent.test.ts, test/isolate.test.ts,
  test/movePiece.test.ts, test/rendererStatic.test.ts -- 35 tests, all
  pass. `npx tsc --noEmit` clean.

WHAT IS STILL OPEN: the individual fine-grained tests in publicClaims.test.ts
and claudeMdIsCurrent.test.ts were kept, not deleted -- their specific,
incident-driven error messages and surrounding checks (the static-floor
guard, the workerFail/workerFailDivergence checks) have real diagnostic
value the consolidated gate does not reproduce, and this project's own
audit protocol names "deleting a hard-won test" as a real cost, not a free
cleanup. The consolidated gate is additive: one more property, checked
once, alongside what already existed. `npm run mutate` re-verification of
all mutations added this session (P4.3, P4.4, P4.6) is still deferred to
when the full suite is safe to run again on this host.
