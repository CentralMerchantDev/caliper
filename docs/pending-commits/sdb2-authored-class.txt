SDB-2 (PLAN.md §6.6): record the class of what each authoring run
produced.

Wrong before: an authored piece carried no record of what KIND of thing it
was (prop, house, condo) -- no mechanic reads this yet, but PLAN.md names
it explicitly as cheap now and expensive to backfill against entries that
never recorded what they were, ahead of V2's own deferred reward table.

authoredClass, not `class`: `class` reads as the JS keyword and, more to
the point, would collide in meaning with the catalogue's existing
`category` field (residential/commercial/etc — the piece's game category,
a different axis entirely from what kind of authoring run produced it).
Both the field name and the closed set (["prop","house","condo"], not an
open string) are disclosed judgement calls -- PLAN.md gives the three as
an illustrative starting set, not a spec -- same rigor as B3's own
UNIQUENESS_MULTIPLIER.

KNOWN_AUTHORED_CLASSES lives in public/catalogue-validator.js, not
catalogue-registry.js, so catalogue-registry.js can import it without a
circular dependency (it already imports validateEntry from there).

Required at two layers: addAuthoredEntry's own pre-check (matching
known-category's pattern), and catalogue-validator.js's new rule 13
(present -> must be a known value) plus an extended rule 10 (the existing
four-field provenance "all-or-nothing" group now covers authoredClass too
-- five fields, still zero-or-all, since every shipped entry has zero).

D1: migrations/0002_add_authored_class.sql -- a SECOND migration, not an
edit to 0001 (which already shipped in the SDB-1 commit; migrations apply
in sequence against whatever state a real database is already in).
NOT NULL requires a DEFAULT under SQLite's own ALTER TABLE rules for a
possibly-non-empty table; 'prop' backfills any pre-existing row (none are
expected yet -- SDB-1 is fresh), and every NEW row still goes through
addAuthoredEntry's own required check regardless of the column default.
entryToRow/rowToEntry (public/catalogue-registry.js) carry authored_class
both directions.
