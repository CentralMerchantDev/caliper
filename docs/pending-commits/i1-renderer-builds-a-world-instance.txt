I1: the renderer builds a world instance -- the first Undone item in Phase I
becomes Done

What was wrong: nine of the thirteen modules built across Phases A-H were
imported by nothing, and public/city-render.js -- the renderer -- still
built its scene from bare `new LandField(16)` / `generateWorld(heightAt)`
calls rather than public/world.js's `createWorld({ seed, layers })`, exactly
as the plan's own Undone notes said at lines 541, 566, 697, 728, 968. The
mechanism was proven in isolation since A4; nothing ran it.

How it's fixed: `buildWorldState(seed, layers)`, exported from
city-render.js and used by `buildWorld()` itself, composes via
`createWorld()` instead of reimplementing plan/terrain generation a second
time. `buildWorld()` now reads `?seed=` from the URL (default
`DEFAULT_SEED`, unchanged behaviour for every call site that does not pass
one). `plan` (the downtown-only slice, from `generateCityPlan`) and `world`
(the whole world, from `createWorld()`'s own `.plan`) stay two separate
values on purpose -- this file already relies on that distinction (`plan.
plots` is 1,374 downtown entries; `world.plots` is the whole ~20,000-plot
world) and `createWorld()` only exposes the latter; `generateCityPlan(seed)`
is memoised by seed since A2b, so calling it again here is a cache hit, not
a second generation.

Test-first, two properties, both named in the ledger: test/
cityRenderWorldState.test.ts watched RED first (buildWorldState did not
exist -- esbuild failed the import outright), then implemented.
  1. For the default seed, buildWorldState()'s field/heightAt/plan/world are
     byte-identical (fingerprinted) to what the old bare calls produced --
     a data-source swap, not a behaviour change.
  2. A named, non-default seed ("shoreline-district-9") produces genuinely
     different field/world fingerprints -- proving the seed reaches
     createWorld() rather than silently defaulting, which property (1) alone
     cannot see (a dropped seed still falls back to the same DEFAULT_SEED).
