The full suite was silently blind to roughly 40% of itself: test/run.mjs's
own import loop has no crash guard, and test/navWheel.test.ts threw an
uncaught exception at module-import time that truncated every test file
imported after it from the reported summary. Found while trying to verify
TER-1..5 for real; not caused by this session, but two of the four instances
found and fixed here were.

WHAT WAS FOUND

Verifying TER-1..5 needed a trustworthy full-suite count. It kept reporting
the identical 665 tests / 633 pass / 6 fail regardless of what changed,
including after three new test files (17 tests, independently proven to
pass standalone) were added. Traced with disk-persisted instrumentation
around test/run.mjs's own `for (const outfile of built) { await
import(...) }` loop (captured stdout alone could not distinguish a real
completion from a truncated one) to the exact cause:

test/navWheel.test.ts reads public/index.html and asserts, AT MODULE TOP
LEVEL -- outside any test() -- that it contains `id="nav-wheel"`. It does
not (the 2026-09-13 Phase 1 holding-page rewrite removed it). The assertion
throws during `import()`. test/run.mjs's loop has no try/catch around that
line, so the throw propagates as an uncaught exception -- confirmed
directly: `node test/run.mjs test/navWheel.test.ts` alone crashes the
process outright with a full stack trace via triggerUncaughtException.
In the FULL suite, node:test's own runner absorbs this differently: the
diagnostic line "A resource generated asynchronous activity after the test
ended... caught by the test runner" (present in every full run this whole
session, always read as unrelated noise until traced) IS this absorption --
and everything imported after the crashing file silently stops being
counted in the final summary, producing a plausible-looking, genuinely
INCOMPLETE total rather than a visible error.

A second, independent instance of the identical defect was found and fixed
in the same pass: test/pickSelection.test.ts read the now-quarantined
public/world-render-3d.js (decision #22) the same way, at module top level,
further along in read-dir order -- crashing the loop a second time, later.

Separately (findings, not this commit's job -- see
docs/DECISIONS-FOR-MARK.md #24 for the full account and recommendation):
test/.built/ is a shared, unlocked build output directory, and four stray
`node test/run.mjs` processes were found running on this machine (ended by
Mark before the authoritative re-run below). That IS a real, separate
hazard, but the crash-and-truncation above reproduced identically with zero
contention -- it was not the primary cause of this specific symptom.
