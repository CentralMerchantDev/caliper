B3 -- the render path, wired into the live page.
public/world-render-3d.js's _buildCityBase now fetches the real,
persisted board (public/board.generated.json, via public/board-load.js's

buildBoardScene(), right after buildWorld() runs.

THE BOOTSTRAP DECISION B2.6 LEFT OPEN, DECIDED: createWorld() is
synchronous; fetchBoard() is inherently async (fetch()). _buildCityBase
was ALREADY async (it already awaits a dynamic import of city-render.js
and two animation frames) -- awaiting fetchBoard() there needed no new
architecture, only one more await in a place that was already one.

SCOPED HONESTLY AS ADDITIVE, NOT A REPLACEMENT, AND WHY: buildWorld()
still runs. Its return value is what picking (P4.1's boardPiecesById),
the spatial index, selection, and sun/sky all key off today -- replacing
it outright would mean rebuilding all four in the same pass, which this
run's own "partial credit" allowance (docs/briefs/RUN2-CLI-2026-09-09.md:
"a render path that draws roads and buildings from the board and
nothing else YET is worth far more than another phase of invisible
correctness") does not ask for tonight. The board's pieces are added as
a second THREE.Group in the same scene instead. A fetch/build failure
is caught and logged, not thrown, since the board is a real addition,
not yet load-bearing for anything buildWorld() itself sets up.
