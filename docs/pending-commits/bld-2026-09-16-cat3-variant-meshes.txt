second mesh per placement, using zero new assets.

Firewatch shipped 23 unique trees for an entire game; Eastshade's own

THE TARGET, CHOSEN FROM THAT BUDGET: BO7A's own UNMATCHED_MESHES table
(scripts/link-catalogue-meshes.mjs, unchanged in spirit since BO7A) had
already benched three real, already-vendored, already-CC0-licensed meshes
-- tower-base-6x6-alt, midrise-4x4-alt, commercial-2x2-alt -- excluded
ONLY because "only ONE catalogue slot of that footprint+category exists,
already taken by another L12 mesh." That is a SLOT problem, not an ASSET
problem: CAT-2's own "no new entries, no changed footprint or category"
still holds (CLI's own fields untouched), but nothing stops a single
catalogue entry from carrying a SECOND real mesh, chosen per placement
rather than per slot. Zero new assets, matching R2's own "far lower than
instinct" -- the opposite of what CAT-3 could have become (commissioning
new meshes for every footprint tier).

THE MECHANISM (public/board-renderer.js):
- `glbVariants`, a NEW, ADDITIVE, OPTIONAL catalogue field alongside the
  existing `glb` -- absent on 47 of 50 entries, so every entry without it
  behaves exactly as before this item (test-proven: "an entry with NO
  glbVariants resolves glb to entry.glb, byte-identical to before this
  feature existed").
- `deterministicVariantIndex(seed, poolSize)`: FNV-1a hash of
  `${typeId}:${id}` mod pool size -- never Math.random(). The SAME real
  placement always resolves to the SAME mesh across re-renders (a rebuild
  after an unrelated click must not make an already-placed piece appear
  to silently change shape), while two DIFFERENT placements of the same
  typeId are very likely to land on different pool indices.
- `glbForPiece(entry, piece)`: returns `entry.glb` unchanged when
  `glbVariants` is absent or empty; otherwise indexes into
  `[entry.glb, ...entry.glbVariants]`.
- Wired into `resolveBoardPieces`'s own existing glb/layer resolution --
  no change to its own returned SHAPE, only which real path `glb` holds
  for a variant-bearing typeId.

THE DATA (scripts/link-catalogue-meshes.mjs, data/catalogue.json):
- `VARIANT_BINDINGS`: `{ "tower-base-6x6-a": ["tower-base-6x6-alt"],
  "apartment-block-a": ["midrise-4x4-alt"], "corner-shop-a":
  ["commercial-2x2-alt"] }`. `UNMATCHED_MESHES` is now empty -- these
  three were its own entire contents.
- `main()` writes `entry.glbVariants` (an array of real glb paths,
  resolved the same way `glb` already is) for exactly these three
  entries, additive, never overwriting `glb` itself. Idempotent, like the
  rest of this script -- a stale `glbVariants` from a prior run is always
  dropped and recomputed fresh, never silently carried forward.
- node scripts/link-catalogue-meshes.mjs: "linked 38 of 50 catalogue
  entries" (unchanged from CAT-2) "3 of those carry a second real variant
  (CAT-3): tower-base-6x6-a, apartment-block-a, corner-shop-a" "0 L12
  meshes have no matching entry" (was 3, all three now variants).
