## CORRECTION, continuation session — item 0's real status, and why this lane could not have known it

The paragraph above is wrong in its conclusion, though the observation it
made was correct. `public/city-render.js:1934` **does** pass `variantSeed:
g.seed` — on `b1-land`. `codex-lane` is a different checkout; that commit
does not exist here and cannot until the branches merge. `grep` against
this worktree correctly found nothing, because there is nothing to find
*in this worktree* — that is not evidence the request went unfulfilled, it
is evidence of where this lane was looking.

**The real process finding, replacing the "unactioned request" framing
above**: the cross-lane request protocol (`docs/CROSS-LANE-REQUESTS.md`)
has a structural blind spot — a requesting lane checks its own worktree
for the other lane's fulfilment, and a per-branch checkout means it can
never see that fulfilment there, no matter how long it waits or how many
runs it checks. This is not a case of the request being ignored, slow, or
lost; it is the mechanism itself being unable to produce a "yes" from this
side of a branch boundary, structurally, every time. Whoever designs this
protocol's next revision needs a status signal that does not depend on
reading the other lane's own files from across a branch line — a written
confirmation in the request doc itself, updated by the fulfilling lane, or
a check against a shared/merged reference rather than each lane's own
checkout.

The three-runs-old "unactioned" framing above is retracted, not deleted
(this project's own practice: correct forward, do not rewrite history) —
what was true from this lane's vantage point (nothing found in this
worktree) is preserved above; what it means is corrected here.
