# P4.7 -- water banding, diagnosed, fix deferred

Mark, and the other lane, reported conspicuous horizontal banding in the sea
surface across every camera. Diagnosis only in this pass -- reasoning below.

## What it is: a repeating normal-map texture, tiled 120x120, on a near-mirror
material, on one 20+ km flat plane

`public/city-render.js:199-213`, `waterNormalTexture()`:

```js
function waterNormalTexture(THREE) {
  const N = 512, c = document.createElement("canvas");
  ...
  for (let i = 0; i < N; i++) for (let j = 0; j < N; j++) {
    const v = Math.sin(i * 0.085) * Math.cos(j * 0.062) + Math.sin((i + j) * 0.041) * 0.75 + Math.sin(i * 0.021 - j * 0.017) * 0.5;
    ...
  }
  ...
  const t = new THREE.CanvasTexture(c);
  t.wrapS = t.wrapT = THREE.RepeatWrapping; t.repeat.set(120, 120);
  return t;
}
```

A 512x512 canvas built from a small number of low-frequency sine/cosine
terms (periods on the order of tens of pixels), then tiled **120 times** in
both U and V across the sea plane's UV space via `RepeatWrapping`.

`public/city-render.js:1459-1470`, the sea material this normal map is
applied to:

```js
const sea = ... new THREE.Mesh(
  new THREE.PlaneGeometry(WORLD.SIZE * WORLD.SEA_SPAN, WORLD.SIZE * WORLD.SEA_SPAN),
  new THREE.MeshStandardMaterial({
    color: 0x2181a6, roughness: 0.055, metalness: 0.5,
    transparent: true, opacity: 0.62, depthWrite: false,
    normalMap: wn, normalScale: new THREE.Vector2(0.42, 0.42),
  })
);
```

`roughness: 0.055` is near-mirror. `metalness: 0.5` makes the specular
response strong and colour-tinted rather than the weak, mostly-white
highlight a low-metalness water material would have. `PlaneGeometry(w, h)`
with no segment arguments is two triangles -- the geometry itself carries no
noise; 100% of the surface's apparent roughness comes from the normal map.

**Put together:** a highly specular material reflects the sky/sun strongly,
and the reflection direction is perturbed by the normal map at 120x its
native tile frequency. Every one of those 120 repeats produces a coherent,
periodic ridge in the reflected highlight. On a plane this large (`WORLD.SIZE`
is 26 km; `SEA_SPAN` widens that further), viewed from a raised or distant
camera -- which is most of this project's own camera presets, per
`scripts/shoot.mjs`'s own view list ("The whole world", "Coast from the sea",
"City + mountains") -- a periodic normal-map pattern under grazing or
elevated viewing angles is a textbook cause of visible banding: the human
eye reads a REGULAR spacing in a specular highlight as bands or rings, not
as texture, especially where the frequency is anisotropic (the i/j
coefficients above, 0.085 vs 0.062, are not equal, so the pattern is not
even isotropic noise -- it has a directional bias, which reads as
directional banding rather than a mottled sparkle).

## Why not the other two named causes

**Precision loss on a large flat plane.** The plane geometry itself is two
triangles with no subdivision -- there is no per-vertex position precision
to lose (no vertex noise is computed at all; the entire visual variation
comes from the fragment-shader-sampled normal map and the separate 512x512
sea-bed depth texture). The depth-driven colour blend
(`public/city-render.js:1014-1029`) uses `smoothstep`, a continuous
function, sampling a bilinearly-filtered `texture2D` -- nothing here
discretises into visible steps. Ruled out by reading the actual blend math,
not assumed clean.

**Depth-buffer quantisation at distance.** The sea mesh sets
`depthWrite: false` (`city-render.js:1467`) specifically so it does not
participate in depth-buffer ordering against itself -- there is no
depth-buffer interaction here that could quantise across the visible
surface. The foam/swash effect (`city-render.js:1035-1038`) is also
`smoothstep`-driven and geographically localised to shorelines (bounded by
`depth`), not a whole-surface effect. Ruled out for the same reason: read,
not assumed.

## Why this pass does not change the code

Fixing this with confidence needs a real render to confirm the diagnosis
against what a camera actually shows, and to confirm a candidate fix
(lower `metalness`/raise `roughness` to reduce specular sensitivity to the
normal map's periodicity, and/or a non-matching, non-round `repeat` count
with a texture built from more, smaller, less-aligned frequency terms so no
single tile boundary reads as a coherent line) actually removes the banding
rather than just moving it. This project's own standard: never report
unverified work as verified.

This session's host has crashed on memory three times today; the standing
rule adopted for the rest of it is not to start a full test suite or a
multi-camera render below 4 GB free, and free memory stayed under that
threshold for the remainder of the time available this pass. The
code-level diagnosis above is real evidence -- the exact repeat count, the
exact material values, the exact shader math ruling out the other two
causes -- but it is not the same as watching a fix actually clear the
banding on a real frame, and this project has a specific, named history
(`docs/AUDIT-PROTOCOL.md` §0's own evidence table) of a plausible-sounding
fix shipping unverified and being wrong.

**Left as a named, evidenced, un-fixed defect**, per Mark's own instruction
for exactly this situation ("if it is not fixable without a bigger change,
say that and leave it") -- the constraint here is verification capacity
this session, not the size of the code change, but the response is the
same: name it precisely enough that whoever picks it up next does not have
to re-diagnose it, and do not ship a guess.

## What a next pass should do

1. `node scripts/shoot.mjs "Coast from the sea"` (or another elevated/wide
   view) once free memory is comfortably above 4 GB, to see the banding
   directly and confirm this diagnosis against a real frame.
2. Try, in order, cheapest first: (a) reduce `normalScale` and raise
   `roughness` a little -- confirms whether specular sensitivity is the
   dominant factor without touching the texture itself; (b) change
   `repeat.set(120, 120)` to a non-round, non-matching pair (e.g. an X/Y
   ratio that shares no small common factor with the plane's own aspect)
   to break the coherent tile-boundary alignment; (c) if banding
   persists, rebuild `waterNormalTexture` from more, smaller-amplitude,
   less-aligned frequency terms (or a proper multi-octave noise) so no
   single term dominates the visible pattern.
3. Re-shoot the same view after each change and compare directly -- not a
   new, uncomparable frame (`docs/AUDIT-PROTOCOL.md`'s own "the reference
   for the corrective pass" rule).
