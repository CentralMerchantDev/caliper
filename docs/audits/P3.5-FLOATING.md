# P3.5 — grade before you build: the floating-edge gate

Evidence for the P3.5 instruction ("there are buildings in the air"). This
document is written in two passes: RED (this section, before any fix) and
GREEN (appended once P3.5.2's four fixes land and the gate is re-run).

## P3.5.1 — the threshold: RULE ZERO, anchor chosen and anchor rejected

Two defensible anchors were on the table.

**(b) CONSTRUCTION — rejected.** ACI 117 / CSA A23.1 finished-level
tolerance is real and citable, but it describes a poured slab on a
construction site, millimetres to centimetres in scale. Transferring it to a
26 km procedural render would borrow a number's authority without borrowing
anything about what it actually measures. Nothing in this project's own
scale relates to it.

**(a) VISIBILITY — chosen.** A gap matters when it would occupy at least
one device pixel in an actual saved view. This is the only anchor tied to
what Mark actually complained about: what he sees. It is also, correctly,
a function of distance — a gap that would read as separated from the
ground at 200 m might not at 3 km, and a flat metre-or-two tolerance
everywhere would either be too strict up close or too loose from a distance.

The threshold is derived from the SEVEN real cameras this project actually
shows to a visitor: the six baseline views
(`scripts/shoot-reference-baselines.mjs`) plus "Container port" — an
existing preset in `public/city.html`'s own `VIEWS` object, chosen because
none of the six baselines frames the container port at all, which is
exactly the "cannot currently be judged from any existing angle" gap
P3.5.3 is asked to close. All seven share `city.html`'s own camera
(`PerspectiveCamera(fov=33, ...)`, `city.html:151`) and the
1400×900 viewport `shoot-reference-baselines.mjs` renders at
(matched here so the threshold is the real one, not an invented one).

For a mesh instance at distance `d` from the NEAREST of the seven cameras:

```
metresPerPixel(d) = 2 * d * tan(fovRad / 2) / viewportHeightPx
```

A gap below that many metres could not read as separated from the ground in
any saved view this project actually takes; at or above it, it visibly
floats or is visibly buried.

## The gate: `scripts/measure-floating.mjs`

Runs the REAL renderer — `public/city.html`, the same Playwright/SwiftShader
harness `scripts/shoot-reference-baselines.mjs` already drives, not a
reimplementation (the exact class of error the project's own
`measure-layout.mjs` fallback made once already, reporting a flat world).

For every Mesh/InstancedMesh **instance** in the live scene graph (per
instance for InstancedMesh — a group-level check misses every one of the
container port's 2,200 instances, which is the specific mistake this gate
exists to not repeat):

- world-space bottom Y of its bounding box
- `heightAt(worldX, worldZ)` beneath it (`window.__world.heightAt`, the
  SAME function city-render.js itself builds the scene with — not a second,
  possibly-diverging computation)
- `gap = bottomY - ground`, flagged when `|gap| >= metresPerPixel(distance to
  nearest of the 7 cameras)`

**A real methodology bug found and fixed before the gate could be trusted:**
the first working version used `.visible` to decide what counts, and a scan
camera far from a feature (e.g. "Downtown skyline" looking at the container
port, several km away) leaves that feature's LOD switched to its EMPTY
culling placeholder — so the scan silently measured nothing there. Zero
`container-port-yard` offenders on the first honest-looking run turned out
to mean "invisible from where I looked," not "clean," the same shape of
failure this whole gate exists to catch. Fixed: for any object that is one
level of a `THREE.LOD`, only level 0 (the real geometry, always) is kept,
regardless of which level the scan camera's own distance happened to select.

**Nothing in the real scene had a `.name` before this pass** (confirmed by
grep — `city-render.js` never set one). Both the allow-list and the report's
own "name of whatever added them" requirement need real identification, not
a guess, so this pass adds `.name` at each construction site directly in
`public/city-render.js` — additive only, zero geometry/behaviour change
(confirmed by the regression suite, see GREEN section).

## The allow-list, each entry with a reason

| pattern | what | why excluded |
|---|---|---|
| `env:*` | terrain, its skirt, ground-fabric water areas, roads (incl. bridge-deck geometry), waterways, the airport's own graded platform + embankment | these ARE the ground or are graded to their own profile — point-sampling one centre against an extended surface is the exact error this gate exists to catch elsewhere; checking it here would be circular |
| `city-sky` | `public/sky.js`'s pre-existing sky group | a sky layer is not ground-relative by definition |
| `*-boat-afloat` | marina moorings, open-bay sail/cargo ships | draught means partly below the water surface by design |
| `marina-pontoon`, `golf-course-pond` | floating dock, water hazard | ride their own water level, not seabed heightAt |
| `boardwalk-railing` | rail on the boardwalk deck | its reference surface is the deck (checked separately), not the ground |
| `pier` | the pleasure pier, its pavilion, and its wheel | stands on piles over open water by design |
| `bridge-span` | bridge deck/pier/tower geometry | spans a gap on piers by design; pier-touchdown verification is a known open gap, already on record in `docs/audits/P3-BRIDGES.md`'s "genuinely open" list |
| `*-roof`/`-cap`/`-dome`/`-spire`/`-pod`/`-cab` | Mark's own named example category | mounted on top of a TALLER part of the same structure (checked separately, unexcluded) — its own bottom answers nothing about whether the structure touches ground |

`building` (the 17,105 plot buildings — this is the population Mark

## P3.5.2 — the fixes

**1. Container yard: graded in a 2D grid, not one mean.** The renderer
cannot cut and fill the real terrain — `heightAt` is a pure function shared
by roads, buildings, and everything else, with no per-feature override
mechanism, and building one is out of this pass's scope (named below, not
pursued). Per Mark's own documented fallback for exactly that case, the
yard now follows the ground in bands. A first attempt banded only by depth
from the quay (Z) and cut the worst gap from 23.9 m to ~15 m, but the
residual offenders all clustered at the SAME x positions near the yard's
outer edge — the relief varies across the quay (X) as much as it does
moving inland, so a 1D strip was still averaging away a real cross-slope.
Replaced with a 2D grid (~150 m across the quay × ~35 m inland), each cell
graded to its own local mean. `stats.containerYardLevel` is now the grid's
own mean (reported for continuity) and `stats.containerYardBands` records
every cell's level. Site relocation (the other half of Mark's instruction —
`findQuay` optimises for water depth and does not vet what is behind it)
was NOT additionally pursued: `findQuay`/`SITE.containerPort` is also relied
on by other code, and changing which site gets found is a materially larger
change with its own regression surface than grading the site that is
already found — named as open, not silently done.

**2. Station: `assessFootprint`, the same check every plot building gets.**
`SITE.station`'s envelope (`features.js`'s own need: `w:240, d:120`) is now
assessed with `public/footprint.js`'s `assessFootprint`, verdict decides the
Y exactly the way `buildScenePlacements` already does for the 17,105
buildings (`base`, or `base + range` for a terrace verdict) — no special
geometry, per Mark's "do not special-case it". A `refuse` verdict now
records to `stats.setPieceRefused` and builds nothing, the same as an
unreachable site already did.

**3. The seven `Math.max(<const>, heightAt(...))` floors: an explicit
refusal, extracted into one pure, unit-tested function.**
`groundOrRefuse(heightAt, x, z)` (`public/city-render.js`, exported)
replaces every one of the seven sites Mark named (station via
`assessFootprint` above; the container-port cranes, the marina clubhouse,
the marina's nine hardstanding boats, the boardwalk's segments, the
stadium, and the cathedral via this helper). `null` means refuse — the
caller records the reason to `stats.setPieceRefused` and does not build —
a real number means real ground, used unmodified, no flooring.

`public/city-render.js`'s own scene-building functions need a GPU
(`test/rendererStatic.test.ts`'s own header: "three.js needs a GPU, so
nothing in the 414 tests builds a scene") and structurally cannot run in
the node test suite. `groundOrRefuse` is pure and THREE-free specifically so
the DECISION is unit-testable even though the renderer it feeds is not:
`test/setPieceRefusal.test.ts`, four cases. **Watched red first, for real**
— `groundOrRefuse`'s body was mechanically reverted to
`Math.max(DRY_ENOUGH, h)` (the exact pattern it replaced), the suite run,
confirmed red on exactly the case that matters:

```
✖ P3.5.2: a site below DRY_ENOUGH is refused, not floated
  AssertionError: a site at 0.3m (wet) must refuse, not return a floored height
  0.6 !== null
```

then reverted to the real fix and re-confirmed green (4/4). Separately, the
real renderer's own end-to-end behaviour was confirmed via `scripts/shoot.mjs
"Container port"`: `stats.setPieceRefused` lists 8 real boardwalk segments
refused for landing on water, in the actual running world, not just in the
unit test.

**4. `public/prop-placement.js` — NOT wired in, and here is why, measured
rather than assumed.** Re-grounding before touching this (per
`docs/BUILD-LOOP.md`'s own discipline) found the premise stale: prop
occupancy checking already exists in `public/city-render.js`, via a
DIFFERENT, working mechanism — `claimProp`/`propGrid`
(`buildProps`, city-render.js ~line 2283), a grid-based reservation the
comment there explains was written deliberately NOT to reuse
`world-registry.js`'s `overlapsReserved` (a road's registry reservation
correctly covers its full carriageway+footway width, which would make
every legitimate prop-on-a-footway placement look like a collision; the
registry has no per-kind filter to distinguish the two questions).
`claimProp` is real and working: it is what the "27 lamp posts standing
inside a bin or a bench" defect `prop-manifest.js`'s own header names is
now measured against (`propRefused` in `stats`, e.g. `{lampPost: 2, bin:
20, bench: 11}` in a real run) — the exact defect class is caught, for
lamps/bins/benches/bus shelters specifically. `public/prop-placement.js`
itself remains genuinely unused outside its own test, exactly as Mark's
brief said — but wiring it in now would mean tearing out a working,
already-measured mechanism to install a materially similar one, pure churn
with real regression risk, not a fix to an open gap. Not done. Also open,
plainly: `claimProp` covers lamps/bins/benches/shelters only — trees, cars,
parasols, containers and boats are not cross-checked against those four or
each other.

## P3.6 — independent verification, then the yard, the reintroduced fail-open, and the two named defects

P3.5 was checked against the repository independently before this pass
started, and it held: zero `Math.max(<const>, heightAt(...))` floors
remained, `groundOrRefuse` was real and in use at five sites, the container
yard was genuinely a 2D grid (not still a single mean under a different
name), and `claimProp` was real and live at four call sites. Refusing
P3.5.2 item 4 (wiring in `prop-placement.js`) on the grounds that the
premise was stale held up under a second, independent read — the mechanism
it would have duplicated was real, not asserted. Finding two bugs in the
gate's own allow-list (the LOD-visibility blind spot, the crane's
boom/cab false positive) before trusting its output is the same discipline
this project's blind audits have already paid for once (the inverted
bearing check, P3-exit) — recorded here because a lane that only reports
its misses on the SCENE side and stays silent about misses in its own
MEASURING TOOL is not really reporting.

### P3.6.1 — the grain was never going to close this; derived, not picked

`YARD_CELL_X = 150` was chosen by analogy ("matching the along-quay spacing
cranes already use") — a resolution borrowed from an unrelated constant,
not derived from what the gate actually requires. Measured directly
(dense 10 m sampling of the real yard footprint, `heightAt` slope between
adjacent samples, both axes): relief 58.0 m across the footprint (matching
Mark's own figure), mean slope 0.043 m/m, p90 0.105, p95 0.113, p99 0.118,
max 0.198.

`cell <= T/s` at the gate's own threshold (~1.5 m near the port camera):

| slope | cell size to hold every gap under threshold |
|---|---|
| mean (0.043) | 34.9 m — close to what was already tried |
| p90 (0.105) | 14.3 m |
| p95 (0.113) | 13.3 m |
| p99 (0.118) | 12.7 m |
| max (0.198) | 7.6 m |

Single-digit metres, exactly as predicted. A container yard graded at a
7–13 m grain does not read as a graded slab; it reads as terrain with extra
steps. **The measurement says the premise — "grade the render finer until
it's flat" — is wrong**, not that a better constant was missed.

**(a) Site relocation, tried, and bounded by real cost, not by will.**
`findQuay` (`public/land-use.js`) now scores the apron BEHIND the berth,
reusing `findFlattestSite`'s own min/max-over-a-grid measure (not a second
implementation), and refuses a berth whose apron exceeds
`footprint.js`'s own `STEP.TERRACE_MAX` (15 m — the existing "a cliff,
nothing should be built" ceiling, transferred rather than invented). Within
the existing search radius (1,500 m) **no site qualifies**; the search was
widened and measured directly against the real terrain field:

| radius | best found | apron relief | moved from `want` |
|---|---|---|---|
| 1,500 (unchanged) | fallback only | 56.3 m | 160 m |
| 3,000–10,000 | same fallback | 56.3 m | 160 m |
| 15,000–20,000 | a real, better site | **23.8 m** | **11,280 m** |

No site anywhere in the world satisfies both constraints — the honest
finding Mark's own instruction names as acceptable. The one materially
better site is 11.28 km away, which is not a grading-resolution problem to
solve, it is a "relocate a major landmark to a different part of the world"
decision, and it is gated by something sharper than judgement: `findQuay`'s
search cost is quadratic in radius (rings × angle-positions-per-ring both
grow with `r`), and radius:20000 was tested directly — the world FAILED TO
LOAD, Playwright's own 120 s navigation timeout tripped mid-generation.
Searching far enough to find the better site is not available in real time
today. `features.js`'s radius stays at 1,500; the fallback-scoring logic
(`findQuay` now always returns its best candidate with `yardOk` and
`yardRange` rather than null) is real and in place for when the search
itself is made cheaper, but is not exercised at a radius that changes the
built site today. Named as the actual reason zero is unreachable via
relocation, not silently accepted as "improved": **owner — a future pass
that either makes `findQuay`'s search sub-quadratic, or makes an explicit
world-design call to move the container port 11 km, understood to place it
somewhere unrelated to its current site.**

**(b) Cut and fill** was not attempted — a new shared terrain-override
mechanism is a larger change than either (a) or the grid, and (a) already
demonstrates the ceiling grading alone cannot reach is a siting problem,
not a rendering one.

**What shipped:** the 2D grid stays (it is real, measured improvement, just
not sufficient alone), `findQuay`'s apron-aware fallback now runs on every
build and reports `yardOk`/`yardRange` even when it cannot relocate,
and the exit condition is answered directly:

**Container yard offenders are NOT zero. 1,633 remain (was 2,022 before
P3.6, 1,679 after the grid alone), worst gap 13.5 m (was 23.9 m, then
18.0 m). Zero is unreachable this pass for the reason measured above.
Owner: the relocation problem named above.**

### P3.7.1 — the mechanism already existed; the fix was never grading, it was grounding

The airport's own embankment (P3.5.2, `env:airport-embankment`) already
built what the container yard needed: a real earthwork, platform plus a
batter carried down to true terrain. The insight this pass acted on: the
container yard had NO ground surface at all under the containers — only
the bare procedural hillside and the containers' own graded band level,
with nothing visually or geometrically connecting the two. Grading the
*containers* closer to real terrain (P3.6.1) reduced the gap; it could
never zero it, because there was still no actual mesh for a container to
rest ON.

**Shared, not duplicated** (`public/city-render.js`):
- `buildEmbankmentSkirt(heightAt, bounds, topAt, segments)` — the airport's
  original 4-edge batter construction, generalised: `topAt(x, z)` is a
  constant for a single-level platform or `(x, z) => bandLevelAt(bands, x,

### P3.7.2 — the airport was the third instance, `Math.max(6, apSite.mean)` was the eighth floor
