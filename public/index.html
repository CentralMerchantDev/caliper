Model routingEach stage runs on the model suited to that stage

Using the most capable model for every call is a mistake in a system meant to run in production. The routing decision asks what each stage actually requires, first. Lower cost is a result of that decision, not the goal of it.

The findingNo quality gap found between the light tier and the frontier tier

32 tasks were run across three tiers: single functions with heavy edge cases, textbook algorithms, and business rules fabricated so nothing could be recalled. At every difficulty level, the light tier reached the same final correctness as the frontier tier, at roughly 36–41% of the cost per correct answer. That ratio held across four separate measurements: the core set at two different repair budgets, the algorithmic tier, and the novel tier. This is the evidence the routing table above is based on.

Each tier was designed to find a gap, not to report whatever happened to run. The core set used edge-case density and a handful of deliberately ambiguous specs. The harder tier used dynamic programming and graph traversal, problems where a real capability gap should show up if one exists. The novel tier used seven business-rule specs fabricated for this experiment, one of them built to contradict a real memorized formula, which rules out memorization as the explanation for the harder tier's clean result. None of the three tiers found a gap.

The practical takeaway

This measures single-function work with a clear specification and an executable test. For that class of work, model choice is a cost decision, not a quality decision. Given a verification loop, the evidence says to default to the tier that fits the job instead of reaching for more capability than the task needs. That is the judgement the routing table above encodes for Ground, Implement, and Retrospective.

ScopeThe limit

Every task at every tier is a single pure function: a fixed signature, a few dozen lines at most, checked against fixed hidden tests. None of it tests multi-file changes, state held across steps, or work where the difficulty is conceptual rather than compositional. Whether a verification loop substitutes for capability on that kind of work is untested here. The world above is a step toward it: a real, stateful system a change modifies in place. Its correctness-critical logic is still, deliberately, pure functions underneath.

"Not recallable" is also not the same claim as "hard." The novel tier rules out memorization as an explanation for the clean sweep across all three tiers; it doesn't establish that composing four or five conditional and arithmetic rules from a spec was cognitively difficult enough to expose a capability gap if one exists.

Spec disagreementVerification fixes slips, not disagreements

On the one task where every model disagreed with the hidden test, the models' answer is arguably the better one. This benchmark is the opinionated party here, not the models.

The task converts camelCase to snake_case. Given parseHTTPResponse, every model, at every capability tier tested, returned parse_http_response. The hidden test insists on parse_httpresponse. That rule is defensible. parse_http_response is at least as reasonable a reading of "convert to snake_case," and more idiomatic.

The finding is not "models are bad at snake_case." Every single cycle on this task failed its first attempt: 0% first-pass, on every rep, across both the two-repair and three-repair sweeps. The disagreement is deterministic, not noise. Repair fixed it most of the time: 13 of 18 cycles across both sweeps converged, mainly because being shown the exact expected string is often enough to get a model to comply against its own judgement. It did not always work. 2 of 9 cycles were still failing the identical test after a second full repair round.

Verification loops fix implementation slips. They do not reliably fix spec disagreements. More repair rounds do not fix that either. When a hidden test encodes a preference rather than a correctness property, the verifier asserts that preference. It does not catch a defect.

IsolationHow the sandbox and world applier work

Earlier builds evaluated patched source text via new Function(). That approach was replaced by AST-free sentinel JSON deserialization, schema validation in memory, and cloned-state mutation with zero runtime code execution.

Where dynamic code execution is required, functions run inside a Cloudflare Dynamic Worker: a fresh V8 isolate per program with empty bindings (env: {}) and disabled outbound networking (globalOutbound: null).

  • Network access: fetch() throws an immediate error.
  • Environment bindings: env returns empty. process and global access are disabled.
  • CPU busy-loop: the isolate is terminated by the CPU time enforcement ceiling.
  • Array expansion: memory limits trigger isolate termination.
  • Recursion limit: RangeError is trapped cleanly within the isolate.

System execution returns explicit error responses without hanging or failing silently.

Methodology

What was run (the cost experiment)

32 tasks total across three tiers: 18 in a core set (string/date parsing, interval and graph work, numeric edge cases, stateful reducers, tolerant parsing of malformed input), 7 in a harder tier (classic dynamic-programming and graph problems), and 7 in a novel tier (fabricated business-rule specs invented for this experiment). Every hidden test's expected value was checked against an independently written reference implementation before any model ever saw a task. Three tiers spanning a real price range, light through frontier. Three repetitions per (task, tier) cell.

How the world's criteria work now

A criterion can no longer assert a computed value a model worked out by hand. That class of claim produced every historical refusal this project tracked. Four kinds remain: existence (a function or field exists and is callable), structural (a field has the right type or count), non-regression (a call's result is compared against the baseline's own output for the same call, computed by actually running it, never supplied by the model), and render (a station or entity type draws without throwing). The hand-authored regression suite is separate. It runs unconditionally on every attempt, unaffected by anything the model proposes.

I don't take a model's word for its own work. At DATUM, every AI answer is scored against a reference computed independently of the model under test. Here, the rule is the same: a non-regression check is only ever compared against the baseline actually running, never a number a model computed by hand. Different project, same rule.
