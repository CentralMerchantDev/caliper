The findingNo quality gap found between the cheapest model and the frontier model

Across 32 tasks in three tiers -- edge-case-heavy single functions, textbook algorithms, and business rules fabricated specifically so nothing could be recalled -- the cheapest model reached the same final correctness as the most expensive one, at every tier, while costing roughly 36–41% as much per correct answer. That ratio held across four separate measurements: the core set at two different repair budgets, the algorithmic tier, and the novel tier. This is the evidence base the routing table above points to.

Each tier was built as a deliberate attempt to find a gap, not a report of whatever happened to be run. The core set applied pressure through edge-case density and a handful of deliberately ambiguous specs. The harder tier applied pressure through algorithmic difficulty -- dynamic programming and graph traversal, exactly the kind of problem where a real capability gap would be expected to surface. The novel tier applied pressure through unfamiliarity, specifically to rule out the possibility that the harder tier's clean result was memorization rather than capability: seven business-rule specs fabricated for this experiment, one of them built to actively contradict a real memorized formula. None of the three attempts found a gap.

The practical takeaway

For single-function work with a clear specification and an executable test -- the class of work measured here -- model choice is a cost decision, not a quality decision. Given a verification loop, the evidence here says to default to the cheapest model that can run in it. That evidence is exactly why the routing table above sends Ground, Implement, and Retrospective to Haiku.

ScopeThe limit

Every task at every tier is a single pure function: a fixed signature, a few dozen lines at most, checked against fixed hidden tests. Nothing here tests multi-file changes, systems that hold state across steps, or work where the difficulty is conceptual rather than compositional. Whether a verification loop substitutes for capability on that kind of work is untested here -- the world above (a real, stateful system a change modifies in place) is the step toward richer work; its correctness-critical logic is still, deliberately, pure functions underneath.

"Not recallable" is also not the same claim as "hard." The novel tier rules out memorization as an explanation for the clean sweep across all three tiers; it doesn't establish that composing four or five conditional and arithmetic rules from a spec was cognitively difficult enough to expose a capability gap if one exists.

Spec disagreementVerification fixes slips, not disagreements

On the one task where every model disagreed with the hidden test, the models' answer is arguably the better one. This benchmark is the opinionated party here, not the models.

The task: convert camelCase to snake_case -- parseHTTPResponse → what? Every model, at every capability tier tested, returned parse_http_response. The hidden test insists on parse_httpresponse. That rule is defensible. parse_http_response is at least as reasonable a reading of "convert to snake_case" -- arguably more readable, certainly more idiomatic.

Given that, the finding isn't "models are bad at snake_case." It's sharper: every single cycle on this task failed its first attempt -- 0% first-pass, on every rep, across both the two-repair and three-repair sweeps -- because the disagreement is deterministic, not noise. Repair fixed it most of the time (13 of 18 cycles across both sweeps converged) simply because being shown the exact expected string is often enough to get a model to comply even against its own judgment. But not always: 2 of 9 cycles were still failing the identical test after a second full repair round.

Verification loops fix implementation slips. They do not reliably fix spec disagreements, and more repair rounds don't reliably fix that either. When a hidden test encodes a preference rather than a correctness property, the verifier is asserting that preference, not catching a defect.

Methodology

What was run (the cost experiment)

32 tasks total across three tiers: 18 in a core set (string/date parsing, interval and graph work, numeric edge cases, stateful reducers, tolerant parsing of malformed input), 7 in a harder tier (classic dynamic-programming and graph problems), and 7 in a novel tier (fabricated business-rule specs invented for this experiment). Every hidden test's expected value was checked against an independently written reference implementation before any model ever saw a task. Three models spanning a real price range: claude-haiku-4-5 (cheapest), claude-sonnet-5, claude-opus-4-8 (frontier). Three repetitions per (task, model) cell.

How the world's criteria work now

A criterion can no longer assert a computed value a model worked out by hand -- that class of claim produced every historical refusal this project tracked. Four kinds remain: existence (a function or field exists and is callable), structural (a field has the right type or count), non-regression (a call's result is compared against the baseline's own output for the same call, computed by actually running it -- never supplied by the model), and render (a station or entity type draws without throwing). The hand-authored regression suite is separate and runs unconditionally on every attempt, unaffected by anything the model proposes.

Where a skeptical reader should push

  • Sample size on convergence rate is small on the core set specifically and has wide error bars there. It doesn't apply to the final-pass-rate numbers, which rest on the full 54 or 21 cycles per model and are the load-bearing ones.
  • Single vendor for the 32-task experiment. The world's own review stage is genuinely cross-vendor (OpenAI reviewing Claude); the cost experiment itself is Anthropic-only.
  • "Not recallable" is not the same claim as "hard." See "The limit" above.
  • No statistical trial sweep across many change requests yet. This build proves the pipeline works end to end and the controls hold under real forcing; it does not yet establish a "reviewed, nothing found" base rate across many kinds of request.

IsolationHow the sandbox works

Every generated function runs inside a Cloudflare Dynamic Worker -- a fresh V8 isolate spun up per program, with no bindings (env: {}) and no network access (globalOutbound: null). Proven adversarially against the live, deployed sandbox -- by writing code that deliberately tries the escape:

  • Network access -- fetch() throws immediately, every time.
  • Reading bindings or environment -- env comes back empty, no process, no leaked globals.
  • A tight busy-loop under a deliberately small CPU budget -- the isolate is killed outright.
  • Unbounded array growth -- the isolate is killed outright.
  • Unbounded recursion -- a catchable RangeError, caught inside the sandbox itself.

In every case the calling code gets an ordinary, catchable error -- never a hung request, never a silent nothing.
