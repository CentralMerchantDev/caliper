The findingNo quality gap found between the cheapest model and the frontier model

Across 32 tasks in three tiers — edge-case-heavy single functions, textbook algorithms, and business rules fabricated specifically so nothing could be recalled — the cheapest model reached the same final correctness as the most expensive one, at every tier, while costing roughly 36–41% as much per correct answer. That ratio held across four separate measurements: the core set at two different repair budgets, the algorithmic tier, and the novel tier. This is the evidence base the pipeline above's routing panel points to when it says a cheaper model was considered.

Each tier was built as a deliberate attempt to find a gap, not a report of whatever happened to be run. The core set applied pressure through edge-case density and a handful of deliberately ambiguous specs. The harder tier applied pressure through algorithmic difficulty — dynamic programming and graph traversal, exactly the kind of problem where a real capability gap would be expected to surface. The novel tier applied pressure through unfamiliarity, specifically to rule out the possibility that the harder tier's clean result was memorization rather than capability: seven business-rule specs fabricated for this experiment, one of them built to actively contradict a real memorized formula. None of the three attempts found a gap. That's the basis for taking this result seriously — three independent, differently designed attempts to break the claim "these models perform the same here," and all three failed to break it. See "The limit" below for what these attempts don't cover.

The practical takeaway

For single-function work with a clear specification and an executable test — the class of work measured here — model choice is a cost decision, not a quality decision. Given a verification loop, the evidence here says to default to the cheapest model that can run in it, not the most capable one. The pipeline above still routes to Sonnet for Implement, because fidelity to a real production build's own routing table is the point of this build, not a cost-minimization exercise — the routing panel says so explicitly rather than implying the choice was about quality.

ScopeThe limit

Every task at every tier is a single pure function: a fixed signature, a few dozen lines at most, checked against fixed hidden tests. Nothing here tests multi-file changes, systems that hold state across steps, or work where the difficulty is conceptual rather than compositional — ambiguity about what to build, not just how to build it correctly. Whether a verification loop substitutes for capability on that kind of work is untested here, and answering it properly would be a different, considerably larger experiment: multi-file tasks need a different sandbox, different tests, and probably a different notion of "correct" altogether. That's out of scope for this project on purpose — the tight, verifiable design of one function, one set of hidden tests, one clear pass/fail is what makes the finding above checkable at all, and stretching it to cover more would trade that away for a weaker result. The pipeline above is a step toward richer work (a full interactive artifact, not a bare function) but its machine-verified core is still, deliberately, a pure function per preset — see "How verification works" further down for exactly why.

"Not recallable" is also not the same claim as "hard." The novel tier rules out memorization as an explanation for the clean sweep across all three tiers; it doesn't establish that composing four or five conditional and arithmetic rules from a spec was cognitively difficult enough to expose a capability gap if one exists. This is a real result, checked carefully across three independently designed attempts — and it remains possible that a task shape none of the three tried would find a difference these didn't.

Spec disagreementVerification fixes slips, not disagreements

On the one task where every model disagreed with the hidden test, the models' answer is arguably the better one. This benchmark is the opinionated party here, not the models.

The task: convert camelCase to snake_case — parseHTTPResponse → what? Every model, at every capability tier tested, returned parse_http_response. The hidden test insists on parse_httpresponse, encoding a narrower, specific rule: only split before a capital letter that immediately follows a lowercase letter or digit, so a run of capitals like HTTP never gets internally separated. That rule is defensible. parse_http_response is at least as reasonable a reading of "convert to snake_case" — arguably more readable, certainly more idiomatic. A careful reader who noticed the disagreement and wasn't told this would reasonably conclude the test was buggy rather than deliberate, so it's said here first rather than left for them to find.

Given that, the finding isn't "models are bad at snake_case." It's sharper: every single cycle on this task failed its first attempt — 0% first-pass, on every rep, across both the two-repair and three-repair sweeps — because the disagreement is deterministic, not noise; every model reaches for the same alternative rule every time. Repair fixed it most of the time (13 of 18 cycles across both sweeps converged: 6 of 9 at a one-repair-round budget, 7 of 9 at two rounds) simply because being shown the exact expected string is often enough to get a model to comply even against its own judgment. But not always: 2 of 9 cycles were still failing the identical test after a second full repair round.

Verification loops fix implementation slips. They do not reliably fix spec disagreements, and more repair rounds don't reliably fix that either. When a hidden test encodes a preference rather than a correctness property, the verifier is asserting that preference, not catching a defect — and there's no signal available from the pass/fail number alone that tells you which one happened. That's a limitation of verification as an idea, not of this implementation.

Methodology

What was run (the cost experiment)

32 tasks total across three tiers: 18 in a core set (string/date parsing, interval and graph work, numeric edge cases, stateful reducers, tolerant parsing of malformed input, and a few deliberately ambiguous specs), 7 in a harder tier (classic dynamic-programming and graph problems), and 7 in a novel tier (fabricated business-rule specs invented for this experiment — a support-ticket scorer, a shipping-fee policy, a loyalty-points calculator, a subscription-proration formula, a badge-assignment cascade, an inventory reorder check, and a discount-stacking calculator). Every hidden test's expected value, at every tier, was checked against an independently written reference implementation before any model ever saw a task — ground truth was verified, not assumed. Three models spanning a real price range: claude-haiku-4-5 (cheapest), claude-sonnet-5, claude-opus-4-8 (frontier). Three repetitions per (task, model) cell. Up to two repair rounds (MAX_ATTEMPTS=3) on the core-set, hard-tier, and novel-tier numbers reported above.

How verification works for the pipeline's interactive artifacts

A Cloudflare Dynamic Worker has no DOM, Canvas, or Web Audio API, so it can't execute a real interactive artifact wholesale. Each preset above is designed so its correctness-critical logic is a pure function (e.g. a pitch-detection algorithm, or a tic-tac-toe move-picker) exposed on window, extracted and run through the exact same SandboxRunner the 32-task experiment uses, against synthetic input with independently-verified expected answers — physics, exhaustive search, a published constant, or a stated rubric, never a guess. A small DOM/AudioContext shim lets the artifact's own wiring code execute headless without crashing, but it isn't a real browser: whether a simulated click actually updates the visible page can only be checked in a real browser, so that class of check runs client-side, in your own browser, after the artifact ships — weaker evidence than the server-side logic checks, disclosed as such next to its results, not presented as equally strong.

Where a skeptical reader should push

  • Sample size on convergence rate is small on the core set specifically (3–11 failed-first-attempt cycles per model per sweep) and has wide error bars there. It doesn't apply to the final-pass-rate numbers, which rest on the full 54 or 21 cycles per model and are the load-bearing ones.
  • Single vendor for the 32-task experiment. The pipeline above's review stage is genuinely cross-vendor (OpenAI reviewing Claude); the cost experiment itself is Anthropic-only and says nothing about cross-vendor capability.
  • "Not recallable" is not the same claim as "hard." The novel tier rules out memorization as the explanation for a clean sweep; it does not establish that the tasks were difficult enough to expose a capability gap if one exists.
  • The client-side interaction check can fail even on a working artifact. Browsers require a real, trusted user gesture to unlock audio playback — a script-simulated click doesn't count. The tuner preset's interaction check can read as a failure purely because of that browser policy, not a defect in the artifact. Shown plainly next to that result, not smoothed over.
  • The cross-vendor reviewer's real behavior on these exact prompts was priced from published rates and a same-content Anthropic call's token counts, not measured live, before this pipeline was built (see docs/REBUILD-PROPOSAL.md §4). Every run of the actual pipeline above is a real, live OpenAI call — that estimate was only ever a pre-build planning number, superseded by every real run you trigger.
  • No statistical trial sweep across the five presets yet. This build proves the pipeline works end to end and the controls hold; it does not yet establish the "reviewed, nothing found" rate for well-built presets, which needs repeated real trials, not a single run's outcome — the next piece of work, not this one.

IsolationHow the sandbox works

Every generated function runs inside a Cloudflare Dynamic Worker — a fresh V8 isolate spun up per program, with no bindings (env: {}) and no network access (globalOutbound: null). This was proven adversarially against the live, deployed sandbox — by writing code that deliberately tries the escape, not by reading Cloudflare's docs and trusting them:

  • Network access — fetch() throws immediately, every time.
  • Reading bindings or environment — env comes back empty, no process, no leaked globals.
  • A tight busy-loop under a deliberately small CPU budget — the isolate is killed outright ("Worker exceeded CPU time limit.").
  • Unbounded array growth — the isolate is killed outright ("Worker exceeded memory limit.").
  • Unbounded recursion — a catchable RangeError, caught inside the sandbox itself, no isolate death needed.

In every case the calling code gets an ordinary, catchable error — never a hung request, never a silent nothing.

One measured caveat that changed the design: the CPU limit has a floor of roughly 2–4 seconds of real wall-clock time before it actually terminates a runaway isolate, regardless of how tight the configured budget is. So this app doesn't rely on it for bounding latency: the parent Worker imposes its own 3-second wall-clock abort on every plain-task sandbox call (the pipeline's richer preset checks run under a longer, still-bounded budget — they do real work, like playing out an exhaustive tic-tac-toe game tree).
